# songo

## About SONGO STUDIO

### 1. Project에 대해

#### 1.1 비전

우리는 사회를 바꾸려는 것이 아니다. 목적은 광고 수익 창출이고, 따라서 유저가 우리 사이트에 체류하는 것이 핵심이며, 실용성보다는 재미, 즉 사람들의 흥미를 끌고 오래 머무를 수 있는 것을 만들면 된다. 대단히 혁신적이거나 꼭 필요한 무언가를 만드는 것이 아니다.

#### 1.2 확장 가능성에 대해

우리 프로젝트 특성상 체류 시간을 위해서라면 이것도 하고 저것도 할 수는 있다. 게임에 대한 아이디어도 많다. 하지만 장차 로니 콜먼이 되겠다, 호날두가 되겠다고 선언하기 전에 팔굽혀펴기부터 하자.

- 확장성은 분명히 있다. 그건 매우 좋은 것이다. 다만 확장을 지금 할 것은 아니다.
- 시작점은 우리가 가장 잘하는 것, 즉 불확실성이 가장 적은 것에서 잡는다.

#### 1.3 우리의 정체성 : AI 인디게임 스튜디오

꼬맨틀, 텍스트 배틀처럼 AI를 활용한 게임은 아직 주류 시장은 아니지만 점점 늘어나는 추세다. 이 흐름의 핵심은 두 가지다.

1. 개발 측면 — AI를 개발 과정에서 사용하기에 개발이 쉬워졌다.
2. 게임성 측면 — 그래픽, 스토리라인, 디테일 같은 전통적인 기준으로 보면 질이 낮다. 하지만 AI가 게임 안에 들어감으로써 기존 방식으로는 불가능했던 게임을 만들 수 있고, 그 새로움과 창의성 자체가 재미가 된다.

즉 이 장르에서 '질이 낮다'는 것은 극복해야 할 약점이 아니라 애초에 경쟁하는 축이 다르다는 뜻이다. 우리가 겨루는 지점은 완성도가 아니라 발상이며, 이는 곧 적은 인원과 짧은 개발 기간이 불리한 조건이 아니라는 의미이기도 하다.

이 조건들을 활용해, 쉽게 만들 수 있지만 참신한 게임들을 여러 개 구상·개발해나간다. 우리는 이 영역을 'AI 인디게임 장르'라 부르며, 우리는 이를 개발하는 스튜디오다.

### 2. Product에 대해

#### 2.1 제품의 비전 — 디지털 에버랜드

우리만의 '아하' 아이디어들이 모여 있고, 실제 유저가 방문해 체류하면서 그 아이디어(게임, 글 등)를 즐기는 공간.

#### 2.2 운영 사이클

아이디어 1 개발 → 공유·홍보 → 회고 및 아이디어 2 개발 시작

따라서 지금은 아이디어 1 개발에 집중한다. 다만 그와 동시에 중요한 것이 하나 더 있다.

#### 2.3 에버랜드를 어떻게 설계할 것인가

- 네이버 블로그, 웹사이트, 앱 등 여러 형태 중에서 우리의 기능을 가장 잘 구현할 수 있는 형태를 설계해야 한다.
- 논의된 방향대로라면 게임을 플레이하며 상대와 겨루고, 전적을 비교하는 식으로 확장될 것이다.
- 다만 이러한 기능들을 지금 당장 개발할 필요가 있는지 따져보면, 아직은 이르다.
- 일단 기본적인 것부터 넣는다. 게임을 만든다면, 게임을 먼저 만드는 것.

---

## 2. 브랜치 전략

브랜치란: 현재 코드를 복사해서 만든 별도의 작업 공간. 브랜치 안에서 무엇을 하든 `main`에는 영향이 없고, 작업이 끝나면 `main`에 반영한다. 여러 브랜치가 동시에 존재할 수 있어서 두 사람이 각자 다른 작업을 병행할 수 있다.

```text
main      ●───●───●───────────●──→
                   \         /
game-ui             ●───●───●
                  (분기)   (합침)
```

`main`은 항상 정상 작동하는 상태로 유지한다. 작업은 브랜치를 따서 하고, 완료 후 Pull Request로 합친다.

작업량이 적어도 이 방식으로 가는 이유는, 규모가 커진 뒤에 방식을 바꾸는 비용이 더 크기 때문이다.

브랜치 이름: 작업 내용으로. `game-ui`, `add-company-data` 등.

---

## 3. 작업 순서

```bash
git pull
git checkout -b 브랜치이름
git add .
git commit -m "작업 내용"
git push
```

GitHub에서 Pull Request 생성 후 상대방이 확인하고 merge한다.

### 각 명령어가 하는 일

| 명령어 | 하는 일 | 언제 |
| --- | --- | --- |
| `git pull` | 원격 저장소의 최신 코드를 내 컴퓨터로 가져옴 | 작업 시작 전 항상 |
| `git checkout -b 이름` | 새 브랜치를 만들고 그 브랜치로 이동 | 새 작업 시작할 때 |
| `git add .` | 수정한 파일을 커밋 대상 목록에 올림 | 커밋 직전 |
| `git commit -m "내용"` | 실제로 기록 | 작업 단위 하나 끝날 때마다 |
| `git push` | 내 컴퓨터의 커밋을 GitHub에 올림 | 작업 마무리 후 또는 중간 백업 |
| Pull Request | 내 브랜치를 `main`에 합쳐달라는 요청 | push 후 |

커밋 빈도: 작업 하나가 끝날 때마다. 하루에 여러 번 해도 되고 잦을수록 좋다. 커밋이 커지면 문제가 생겼을 때 되돌릴 지점이 없다.

PR 생성: push 후 GitHub 저장소 페이지에 `Compare & pull request` 버튼이 뜬다.

누가 merge하나: 기본적으로 상대방이 코드를 보고 `Merge`를 누른다. 자기 PR을 자기가 합치면 리뷰가 사라지고 `main`에 직접 push하는 것과 같아진다.

| 상황 | merge 주체 |
| --- | --- |
| 기본 | 상대방 |
| 상대가 오랫동안 확인 못하면 | 본인 |
| 오타, 문서 수정 등 사소한 변경 | 본인 |

## 4. 영역 분리

8/17 기준 영역이랄게 아직 없지만 암튼 한 사람이 한 영역을 맡는다.

| 영역 | 담당 |
| --- | --- |
| `web/` | 프론트엔드 |
| `api/` | 백엔드 |
| `games/` | 게임 로직 및 콘텐츠 |

이유: 같은 파일을 두 사람이 동시에 수정하면 Git이 어느 쪽이 맞는지 판단할 수 없어 충돌(conflict)이 발생한다. 충돌은 수동으로 해결해야 하고, 익숙하지 않으면 시간이 많이 든다. 서로 다른 폴더만 건드리면 충돌이 구조적으로 발생하지 않는다.

## 5. 초기 세팅(8/17 기준 완료됨)

폴더 구조와 브랜치가 아직 없는 상태다. 뼈대는 한 사람이 먼저 올린다.

1. 송현이 폴더 구조와 기본 파일을 `main`에 올린다.
2. 고병연이 `git pull`로 받은 뒤 작업 시작.

동시에 진행하면 충돌이 확정적으로 발생한다.
